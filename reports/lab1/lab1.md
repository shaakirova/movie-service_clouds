## 1. Настройка HTTPS

Для nginx настроили HTTPS с самоподписанным SSL-сертификатом. В конфигурации добавили отдельный сервер для порта 80, который перенаправляет все HTTP-запросы на HTTPS, и сервер на порту 443 с подключённым сертификатом.

После настройки проверили конфигурацию и работу сервиса. Запрос по HTTP возвращает `301 Moved Permanently` и перенаправляет на `https://movies.local/`, а сайт и API по HTTPS возвращают `200 OK`.

## 2. Настройка nginx

Сначала установили nginx через Homebrew и запустили его локально. Для проекта создали отдельный конфиг `movies.conf` и настроили nginx на раздачу frontend.

После настройки проверили конфигурацию командой `nginx -t` — ошибок не было.

![Проверка конфигурации nginx](lab1_images/03-nginx-test.png)

После перезапуска nginx сайт My Movies открылся по адресу `http://localhost:8081`.

![Frontend через nginx](lab1_images/04-frontend-before-api.png)

На этом этапе nginx уже отдавал frontend, но API ещё не был подключён, поэтому сохранённые в PostgreSQL фильмы на странице не отображались.

### Подключение backend

Дальше подключили backend. Flask запустили на порту 5000, а в конфиг nginx добавили проксирование запросов `/api` на Flask.

![Проксирование API](lab1_images/05-api-proxy-config.png)

Проверили работу через `curl` — запрос через nginx вернул `200 OK` и фильмы из PostgreSQL.

![Проверка API через curl](lab1_images/06-api-curl.png)

После подключения API сохранённые фильмы снова появились на сайте. Теперь frontend отдаёт nginx, а запросы к базе проходят через Flask.

![My Movies после подключения API](lab1_images/07-frontend-with-movies.png)

## 3. Запуск двух backend

Дальше для балансировки запустили две копии Flask backend на разных портах — 5001 и 5002. Каждому backend добавили свой идентификатор `backend-1` и `backend-2`, чтобы было видно, какой из них обработал запрос.

Проверили оба backend отдельно через `curl`. Оба вернули `200 OK`, а в `X-Backend-Instance` видно, что первый запрос обработал `backend-1`, а второй — `backend-2`.

![Проверка двух backend](lab1_images/08-two-backends.png)

### Балансировка nginx

Настроили балансировку между двумя backend через `upstream`. В конфиг nginx добавили оба backend на портах 5001 и 5002, а запросы `/api` направили на эту группу.

![Upstream nginx](lab1_images/09-upstream-config.png)

Потом отправили несколько одинаковых запросов через nginx. По `X-Backend-Instance` видно, что запросы по очереди обрабатывают `backend-1` и `backend-2`, значит балансировка работает.

![Результат балансировки](lab1_images/10-load-balancing.png)

## 11. Задание со звёздочкой

Для проверки безопасности nginx были выбраны три возможные уязвимости:

1. доступ к служебным и конфигурационным файлам;
2. доступ к административным и служебным разделам без авторизации;
3. использование потенциально небезопасных HTTP-методов.

Сайт: `https://legendafitness.ru/`

### 11.1 Проверка доступа к служебным файлам

Проверили возможность доступа к служебным файлам `.env` и `.git/config`, которые при неправильной конфигурации сервера могут содержать конфиденциальные данные.

При обращении к обоим адресам сервер вернул `405 Method Not Allowed`. Получить содержимое служебных файлов не удалось.

![Проверка служебных файлов](lab1_images/30-star-service-files.png)

**Результат:** уязвимость не обнаружена.

### 11.2 Проверка административных и служебных разделов

Была проверена доступность стандартных административных адресов `/admin`, `/administrator`, `/dashboard` и `/login` без авторизации.

Для `/admin` и `/administrator` сервер вернул `200 OK`. Запросы к `/dashboard` и `/login` вернули `302 Found` и перенаправили соответственно на `/wp-admin/` и `/wp-login.php`.

Таким образом, удалось определить используемые сайтом стандартные адреса панели WordPress, однако открытый доступ к административной части без авторизации подтверждён не был.

![Проверка административных путей](lab1_images/31-star-admin-paths.png)

**Результат:** уязвимость не обнаружена.

### 11.3 Проверка HTTP-методов

В ходе проверки были отправлены запросы методами `OPTIONS` и `TRACE`.

На запрос `OPTIONS` сервер вернул `200 OK`. При этом в ответе не был указан заголовок `Allow` с потенциально опасными методами. Запрос методом `TRACE` вернул `405 Method Not Allowed`, то есть данный метод на сервере запрещён.

Дополнительно в HTTP-заголовках была обнаружена информация об используемом серверном ПО: `nginx-reuseport/1.21.1` и `PHP/7.4.33`.

**Результат:** использование небезопасных HTTP-методов не обнаружено. Сервер раскрывает версии используемого программного обеспечения.

![Проверка HTTP-методов](lab1_images/32-star-http-methods.png)
